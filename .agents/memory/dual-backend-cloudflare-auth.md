---
name: Dual backend Cloudflare vs Node auth mismatch
description: How to spot and fix "Falha na conexão"-style errors caused by parallel Node/Express and Cloudflare Pages/Worker backends drifting out of sync on auth logic.
---

Some imported projects ship two parallel backend implementations for the same frontend: a Node/Express server (for local/Replit dev) and a Cloudflare Pages Function or Worker (for production, using D1 instead of SQLite). The frontend is shared and offline-first: login screens generate a client-side `.local` token (base64 JSON payload + `.local` suffix) immediately so the user can work offline, then try to silently exchange it for a real server JWT in the background.

**Why this matters:** if the Cloudflare-side `getAuth`/auth middleware only verifies real JWTs and doesn't special-case the `.local` token format, every authenticated request (e.g. POST /fire) made while the client is still holding the `.local` token returns 401. The frontend's fetch wrapper often treats *any* non-OK response as a network failure (checks `res.ok` before parsing), so the user sees a generic "connection failed, saved offline" message even though the app is fully online and the server is reachable — the real bug is an auth format mismatch, not connectivity.

**Critical trap — multiple candidate source files, only one is actually deployed.** A repo can contain several Cloudflare backend variants that look plausible (e.g. `_src/functions/[[catchall]].js` following the Pages Functions convention, a root-level `worker-entry.js`) while the file Cloudflare Pages *actually* serves is a separate pre-bundled `_worker.js` sitting inside the publish/build-output directory (e.g. `app/public/_worker.js`). Cloudflare Pages "Advanced Mode": if `_worker.js` exists at the root of the build output directory, it takes over ALL routing and the `functions/` directory is ignored entirely. Editing the readable source files has *zero effect* on production if the stale bundle isn't regenerated. Confirm which file is authoritative by grepping the actual `_worker.js` bundle for expected route strings/tokens (e.g. `grep -o "auth/combatente" app/public/_worker.js`) before declaring a fix complete — don't assume based on file names or which one looks "more like source".

**How to apply:**
1. When "falha de conexão" reproduces consistently (not intermittently) on a Cloudflare-deployed variant with a working Node/Express counterpart, diff the two backends' auth logic first.
2. If a bundled `_worker.js` exists in the Pages build-output directory, treat IT as ground truth for what's deployed, not the readable source files — grep it directly for the expected logic/route strings.
3. If the bundle is stale/minified and hand-patching is impractical, find or recreate the build step (bundle the readable source, e.g. `worker-entry.js`, with esbuild: `--bundle --format=esm --platform=browser --target=es2022`) and regenerate `_worker.js` from it, preserving any hand-written wrapper logic already present at the tail of the old bundle (e.g. PWA cache-control headers, SPA 404→login.html fallback) by re-adding that wrapper around the new bundle's default export.
4. Add a `package.json` build script (e.g. `build:worker`) so regenerating the bundle is a documented, repeatable step instead of a one-off — future source edits are worthless if nobody remembers to rebuild the deployed bundle.
